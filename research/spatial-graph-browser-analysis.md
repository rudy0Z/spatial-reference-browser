# Spatial Graph Browser — Analysis & Build Plan

**Prepared for:** a non-developer founder who will build ("vibecode") a spatial graph browser with AI help.
**Date:** 2026-11-12
**The product idea:** a browser where your tabs are not a strip at the top but **cards on an open canvas**, connected by **lines that show how you got there** — a map of your research session that you can pan, zoom, arrange, and return to.

## How to read this report

Every technical term is explained the first time it appears. The recurring cast:

| Term | Plain meaning |
|---|---|
| **Electron** | A toolkit for building desktop apps out of web technology. It bundles the Chromium browser engine (the same core Chrome uses), so a "browser built on Electron" is a real Chromium browser with your own interface painted around it. |
| **Main process** | The app's "brain": one Node.js program that owns windows, tabs, settings, files, and security decisions. In this codebase it lives in `src/main/`. |
| **Renderer** | Each web page's sandboxed copy of Chromium that actually draws and runs that page. |
| **WebContentsView** | Electron's object for "one web page rendered as a rectangle you can position anywhere inside a window, and stack above or below other rectangles." This single primitive is what makes a spatial canvas of *live* web pages possible. |
| **IPC** (inter-process communication) | Message passing between the brain and the page sandboxes. Every message crosses a security boundary. |
| **Preload** | A small bridge script injected into a page that exposes a *limited*, hand-picked set of functions instead of full system access. |
| **Node / edge** | Graph vocabulary: a **node** is one page-card on the canvas; an **edge** is the line connecting two nodes ("I clicked this link from that page"). |
| **Embedding** | A way for AI to turn text (a page title + description) into a list of ~384 numbers so that "similar meaning" pages get similar numbers — used to auto-group cards. |
| **Pure module** | A code file with no Electron imports — plain logic that can be tested with a simple `node --test` run without launching the app. Blanc uses this pattern heavily and it is worth copying. |

# 0. TL;DR

1. **The idea has been tried many times and keeps dying commercially** — Firefox Panorama (2011–2016, removed at ~0.01% of *all Firefox users*), Opera tab stacking (2010–2013, lost in an engine rewrite), Arc Spaces/Easels (2022–2026, killed with Arc), and the canvas-browsers Kosmik (sunset May 31, 2026) and Stack (abandoned). No mainstream vendor has ever gone *back* to spatial after trying alternatives.
2. **Yet the psychology is real:** Microsoft Research's Data Mountain proved in 1998 that spatial placement measurably improves finding things again; spatial memory just works best for *small, stable, personally-built* sets — not dozens of transient tabs.
3. **The honest UX answer:** spatial-graph browsing is *genuinely different*, and *better for a committed minority* (power users, professionals with recurring project tab-sets). It has never won mass adoption because it asks the user to pay an organization cost up front, while search pays nothing — and every surviving browser converged on "cheap groups + search + AI suggestions" instead.
4. **The niche has no shipping-at-scale player:** the closest commercial competitors are dead or dying in 2026, the survivors (Milanote, Are.na, Heptabase, Workona) are clip-to-canvas SaaS tools rather than browsers, and the only live products actually in the lane — Marble and Deta Surf — are early betas with no published users or revenue (try them both before writing code — see section 3). The graveyard is the cautionary tale, not a green light to repeat it.
5. **The winning design is "the system pays, the user confirms":** auto-spawn child nodes on link clicks, auto-hibernate with thumbnails, suggest-only clustering, search-first retrieval. Manual curation as the primary interaction is the pattern that failed every time.
6. **Build on a fork of Blanc** (an MIT-licensed open-source browser by Bananify Creative — code at [github.com/bnfy/blanc](https://github.com/bnfy/blanc), site [blanc.day](https://blanc.day); you already hold a full clone at `research/blanc-src`, v1.48.0): plain JavaScript, runs with `npm install` + `npm start`, and its architecture — per-tab WebContentsViews positioned by coordinates plus a transparent overlay layer — *is* the spatial-canvas skeleton, with the nastiest platform bugs already debugged in source.
7. **All four core mechanics are buildable on Blanc:** unified storage nodes (≈80% exists: hibernation, wake, versioned session save), automatic mind-mapping (an interception *skeleton* already exists at `src/main/tab-view.js:495-514` **[verified this session]** — generalizing it into graph semantics is new work with real fragility; see mechanic 2), drag-and-drop docking (most new UI work), and semantic clustering (half the pipeline ships as pure, testable Blanc code — `src/main/tab-import-organizer.js:237,268,370` **[verified this session]**).
8. **The one hard technical limit:** during canvas pan/zoom you must move every live page view every frame, and Electron offers no fast path — so cap simultaneous live views (6–8) and make hibernation cheap so the cap is painless.
9. **Biggest risk is product economics, not code:** if the browser doesn't pay the organization cost itself, it repeats the graveyard. Second risk: scope discipline — the brain file is 17,450 lines **[verified: `wc -l` = 17450]**, so build the graph as *new modules*, not in-place edits.
10. **Reality check on my verification:** I ran source reads/greps only — I did **not** run `npm install`, `npm start`, the test suite, or any build. The first thing to do is Phase 0 step 1: get the stock browser running on your machine.

# 1. How Blanc is built

## 1.1 The one-sentence architecture

Blanc is a frameless Electron window **whose own web page is the browser chrome** — the floating "Island" pill you see is literally the window itself — and every web page you open is a separate WebContentsView stacked *above* that chrome at a computed rectangle, with one more transparent WebContentsView layered on top for popovers (the expanded island, permissions, tooltips).

That inversion (chrome = the window's document; pages = floating layers) is precisely the skeleton a spatial canvas needs: a canvas document underneath, live page rectangles above it, and a trusted overlay on top.

## 1.3 How a tab works (the part you'll extend)

- **One constructor, one wiring function.** Every per-tab WebContentsView is built in exactly one place — `createTabView` (`src/main/tab-view.js:97-108` **[audit]**) — and every event listener is attached in `wireTabView` (`tab-view.js:182-804` **[audit]**), which records precisely which listeners *it* added so teardown removes only Blanc's own handlers, never a blanket `removeAllListeners()` (which crashes Electron's window-open pipeline — documented at `tab-view.js:160-167` **[audit]**). Because wiring is replayable, a hibernated tab can be re-woken with identical behavior — this kills the classic bug class of rebuilt tabs joining the wrong session.
- **The tab record lives in the brain.** `createTab` (`src/main/main.js:9457` **[verified this session]** — a grep returned its full one-line signature, which accepts `openerTabId`, `adoptView`, `restoreHistory`, `asleep` and more; the *signature* is verified, while the downstream behavior of each parameter is per audit, not re-verified) builds a per-tab record; a registry (`window-runtime-registry.js:20-230` **[audit]**) holds one pure, Electron-free record per window: tab order, selection, groups, splits, closed entries, island state.
- **Switching tabs is hide-and-restack.** `setActiveTab` (`main.js:9819-9967` **[audit]**) detaches the old view, attaches the new one, then calls `restackAboveTabViews` (`main.js:9719-9727` **[audit]**) to re-raise every floating surface above pages. Child views have no layout engine — z-order is manual and must be re-asserted after every attach.
- **Platform bugs already solved.** On Linux, views are never detached from the window (a re-added view can go permanently invisible in Electron 44), and a 1×1 transparent "nudge" view is inserted and removed to force a redraw (`src/main/tab-view-lifecycle.js:10-39` **[audit]**). On Windows there's a matching delayed-removal workaround (`main.js:2445-2451` **[audit]**). These are exactly the landmines a spatial canvas of many live views would hit; Blanc stepped on them so you don't have to.
- **Hibernation ("Quiet Tabs") exists.** A 30-second sweep discards background renderers under a pure eligibility policy (`src/main/tab-sleep.js:37-102` **[audit]**), with two discard paths — kill the renderer but keep the hidden view when the page has `sessionStorage` (so form state survives), otherwise destroy the view keeping a navigation-history snapshot. Wake goes through `wakeTab` (`main.js:3124-3226` **[audit]**) with coalescing. This is ~80% of your "dock & hibernate" mechanic, free.
- **Closed tabs have a 3-tier undo** (`src/main/closed-tabs.js:38-56` **[audit]**) that can park the still-live view inside the undo entry for 30 seconds — instant undo with full page state.

## 1.4 Deep-dive: how the notch (the Island) actually works

This is the single most instructive subsystem in the repo for your project, because it demonstrates every pattern you'll need: one transparent layer, one pure geometry module, main-side timing, one-number-per-frame IPC, and paranoid trust gating.

### (a) One view, many modes

The expanded island is **not** a separate window. `createOverlay()` (`src/main/main.js:5554-5605` **[verified this session]** — I read this function line by line) builds a single long-lived `WebContentsView` with `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false` (lines 5559-5567), sets its background to fully transparent `#00000000` so only what the overlay document paints is visible (line 5587, with the comment "Fully transparent: the panel floats over live web content"), loads `blanc-chrome://overlay/` **once per window** (line 5590), and — critically — replays any show request that arrived before the document finished loading, so "an invisible view blocking clicks" can never happen (comment at 5592-5593, replay at 5594-5605).

Every "mode" of the island (panel, command palette, find, shield, spaces switcher, glance…) is **the same one view**, switched by a single atomic `overlay:show` payload carrying `{mode, prefill, purpose, pillRect, searchPriorityResults}` — sent by `showOverlay` (`main.js:5781-5824` **[audit]**), which also *raises the view by re-adding it* to the window's content stack (re-adding raises without detaching — `src/main/overlay-view-lifecycle.js:3-18` **[audit]**). The fixed bottom-to-top stack order is documented right in the code: *tab < fill capsule < overlay < permission prompt* (`main.js:5784-5788` **[audit]**). Hiding sends `overlay:hide` **before** detaching, because the retract animation needs pixels on screen (`main.js:5842-5895` **[audit]**).

> **Copy this:** one persistent transparent child view reused for every popover state, with an atomic show payload and a first-load replay. It eliminates multi-window z-order fights and per-open load latency.
> **Avoid this:** detaching/reattaching child views on Linux/Wayland — Blanc keeps the view window-owned and hides it with `setVisible(false)` there (`overlay-view-lifecycle.js:9-18` **[audit]**).

### (b) Auto-hide: policy in a pure module, timers in the brain

All the *rules* live in `src/main/island-autohide.js` — a pure module with no Electron import. I verified its constants directly (**[verified this session]**): a 10px top-edge reveal band (`REVEAL_EDGE_PX = 10`, line 21), a 40px dwell band requiring a 300ms rest within 8px of drift (lines 29-33), cursor sampling every 120ms while hidden (line 37), and hide checks every 450ms — or 120ms when floating, "it covers the page, so it leaves at once" (lines 41-43). The brain (`main.js`) owns the actual timers and cursor sampling: `watchIslandReveal` polls `screen.getCursorScreenPoint()` every 120ms with a Wayland fallback where the global cursor reads (0,0) (`main.js:3905-3924`, `3844-3882` **[audit]**), and reveals/hides animate with a 160ms/200ms ease-out slide that moves page views via `slidingBounds` — keeping the final (taller) height so the page re-lays out once, not per frame (`main.js:3968-4029` **[audit]**).

A wonderfully specific workaround: on Windows/Linux, a chrome document that is *fully* covered by page views is marked occluded by Chromium (`visibilityState: hidden`) and its geometry reports go stale — so Blanc leaves a 1-pixel row uncovered (`island-autohide.js:157-198` **[audit]**). And because a transparent pixel still takes clicks, the floating pill gets a shadow-only padded box (`island-autohide.js:157-162`, `230-237` **[audit]**).

> **Copy this:** policy constants in a pure module, timers in the brain. Every weird constant encodes a real measured bug — and each is testable without launching Electron.

### (c) Proximity: one number, one frame, no feedback loops

When the cursor nears the pill, the island gently grows. The measurement happens **in the brain, not the chrome renderer** — because the cursor lives over the *page* view, which the chrome document never sees (`main.js:3646-3655` **[audit]**). Closeness is a smoothstep curve over a 250px→80px band to the pill's *rectangle* (not its center) — `src/main/island-proximity.js:17-60` **[audit]** — throttled to one send per ~16ms frame, only on change, with exact-zero snapping so IPC goes silent when idle (`main.js:3691-3712` **[audit]**). The renderer eases toward that one number per display frame and paints it as a CSS variable that becomes `translateY(-2px·k) scale(1+0.02·k)` (`src/renderer/renderer.js:1789-1840`, `src/renderer/styles.css:1299-1346` **[audit]**).

The subtlest trick in the repo: the renderer reports the pill's **resting** box with the effect's own scale/rise divided back out — *"Reporting the transformed box would let the pill chase itself"* (`renderer.js:1717-1754` **[audit]**). If you ever compute geometry from something you're actively transforming, you need this trick, or you build a size↔distance feedback loop.

### (d) Geometry: one pure function to place everything

`calculateChromeLayout` (`src/main/chrome-layout.js:58` **[verified this session]** — I read the signature and body through line 99) takes window size, chrome height, and — the key field — `islandHeight`, *"where the Island sits, when that differs from where the page starts: a floating Island is shown while the page keeps the top of the window"* (comment at lines 62-64). It returns every rectangle: page bounds (`x: railWidth, y: stripHeight`, lines 90-95), island bounds, panel/palette bounds that cover the page pane so the island "expands in place", find-bar bounds, rail and drag-band bounds — plus a compression rule that shrinks the optional tab rail to keep ≥392px of page at the window's 640px minimum width (lines 75-83). The module exists precisely so that edge case is testable without Electron.

The window is created `frame: false` and its own document **is** the strip (`main.js:13264-13324` **[audit]**); the strip reports its real drawn height via `chrome:layout` IPC (a `ResizeObserver` in `renderer.js:1704-1710` **[audit]**), which triggers `resizeActiveView` (`main.js:7277-7338` **[audit]**) — **the single function that repositions every child view** (pages, split panes, glance card, overlay, permission views) on every layout change. Island size presets are three `{zoom, stripHeight}` pairs — 1.15/68px, 1.3/76px, 1.45/84px — mirrored between main (`src/main/island-size.js:9-27` **[audit]**) and CSS, so CSS stays the source of truth and main only caches a pre-draw default (`main.js:13253-13256` **[audit]**).

> **Copy this:** one pure layout function returning every rect, with `islandHeight` decoupled from `chromeHeight` — that single field is what makes a floating (and later, canvas-positioned) island possible. And one re-layout entry point, not per-view listeners.

### (e) Focus, Escape, and click hand-back — choreographed in the brain

`showOverlay` focuses the overlay's page, *except* the passive Ctrl+Tab switcher card, which takes no focus so the key release lands where the keys are (`main.js:5759-5763` **[audit]**). Escape is intercepted in the main process via `before-input-event` so it works regardless of which element has focus (`main.js:5607-5624` **[audit]**). Blur-dismissal is deferred with `setImmediate` (a synchronous dismissal can crash Electron's native detach — the CHECK-crash comment at `main.js:5629-5644` **[audit]**) and has an explicit exception list: find mode, display-share, an open context menu (with an 80ms GTK async-focus sample to avoid false positives), an active island drag, and acceptance-test mode. When the island closes, focus returns either to the page — or, on Escape/cancel, to **the exact pill control that opened the popover** (`restoreTrigger`, `main.js:5896-5933` **[audit]**) — an accessibility win worth copying. Drag state is accepted only from the registered overlay surface *and* only in panel/palette modes (`src/main/overlay-drag-state.js:7-24` **[audit]**); "pill covered" is gated on an explicit renderer report `overlay:panel-drawn` rather than both layers hiding on the same tick (`main.js:12112-12118` **[audit]**).

### (f) Trust: every message through a two-factor gate

Chrome IPC is wrapped by `chromeOn`/`chromeHandle` (`main.js:11369-11400` **[audit]**) which resolve the sender to a *registered* window runtime — with the literal comment "Never fall back to whichever window is focused" — then verify identity three ways in a pure module: the sender must **be** a registered surface's live WebContents, from its **main frame**, on the **exact packaged URL** (`src/main/ipc-trust.js:15-24` **[audit]** — a navigated-away chrome surface loses authority even though the object is unchanged). The bridge itself is only exposed to five exact `blanc-chrome://` documents (`src/main/preload.js:20-28` **[audit]**). The `blanc-chrome://` scheme serves each host from a **fail-closed per-host asset allowlist** in an in-memory, non-persistent session (`src/main/chrome-protocol.js:10-24, 37-41, 119-146` **[audit]**). And the one free-text payload a renderer can send (type-to-open prefill) is re-validated in the brain by a validator *deliberately stricter* than the renderer's own — because *"a renderer is never trusted to have run its check"* (`src/main/island-typing.js:6-33` **[audit]**). Internal `blanc://` pages get a per-host least-privilege bridge instead of one shared API (`src/main/tab-preload.js:60-330`, `src/main/pages-ipc-trust.js:17-26` **[audit]**), so one compromised internal page can't inherit another surface's powers.

> **Copy all of it.** For a browser — an app whose job is to render hostile web content — this trust posture is not gold-plating; it's the difference between a browser and a drive-by download.

## 1.5 What this means for your product

Blanc gives you, debugged and shipped: live page rectangles positioned by coordinates (`setBounds`), a transparent overlay layer above them, pure geometry and policy modules with tests, renderer hibernation with a working wake path, a versioned session format, and a hardened IPC trust model. The spatial browser is, roughly: **replace "one page fills the pane" with "N pages fill their node rects," teach the tab record about position and edges, and give the window's own document a canvas job.** Sections 5 and 7 make that concrete.

# 2. Has anyone done this before?

### Direct answers

- **Has any browser tested or commercially implemented spatial graph browsing?** Yes — repeatedly, for nearly three decades. It shipped in mainstream browsers at least twice as a spatial feature (Firefox Panorama 2011–2016; Opera tab stacking 2010–2013), once as the most ambitious hybrid (Arc Spaces/Easels 2022–2026), and as standalone commercial canvas-browsers (Kosmik, Stack). Microsoft Research validated the *psychology* in 1998–2004 but never productized it.
- **Why has it not won?** Not because the psychology is fake — because the *economics* are wrong for the mass market: measured usage of shipped spatial features was tiny — Panorama at roughly **0.01% of all Firefox users** (a whole-browser share, from the developer's own removal post) versus Arc Spaces at **5.52% of Arc's own daily active users** (a within-Arc share, from the company's letter). The two numbers are not directly comparable — different products, eras, and denominators — but both point the same way: even among users who deliberately chose the more organized browser, the spatial feature stayed marginal. Beyond the numbers: manual spatial curation has an ongoing cost that search doesn't, spatial memory breaks when layouts reflow, and the features were expensive to maintain. Removals were cost/benefit decisions; the one company with the most data wrote that Arc was "too different, with too many new things to learn, for too little reward."
- **Is it a genuinely different and better UX?** Different, yes — measurably, spatial placement aids recall. Better — only for a specific population (committed power users and professionals with stable, recurring, personally-built tab sets) and only if the *system* pays the organization cost. Section 4 gives the full evidence.

| 2022–26 | **Arc Spaces & Easels** | Workspaces with own tab sets; Easels = a real canvas ("essentially a whiteboard") inside the browser — the most spatially ambitious mainstream implementation ever shipped | May 2025: Arc in maintenance mode; Sept 2025: The Browser Company sold to Atlassian for $610M; Dec 22, 2026: Arc stops working (that date single source: [The Verge](https://www.theverge.com/tech/1016832/arc-browser-shutting-down), [Arc release notes](https://resources.arc.net/hc/en-us/articles/22513842649623-Arc-for-Windows-2023-2026-Release-Notes)). The kill data: **only 5.52% of Arc's daily active users regularly used more than one Space** (a within-Arc share, not comparable to Panorama's all-Firefox figure) and CEO Josh Miller wrote Arc was "too different, with too many new things to learn, for too little reward… We knew. We were just in denial." (single source: [Letter to Arc members](https://browsercompany.substack.com/p/letter-to-arc-members-2025)) |

**The pattern is remarkably consistent:** technically successful, emotionally beloved by a minority, commercially removed — for low usage and high complexity (Panorama), collateral damage of an engine rewrite (Opera), strategic pivot to AI (Arc, Opera), or reliability cost (Edge). Across five vendors, **every company that survived the experiment landed on low-effort grouping + search + AI assistance, and none went back to a manual spatial canvas.** That is the strongest signal in this entire report: the failure was never the *idea* of spatial organization — it was asking users to *pay for it* by hand.

Also relevant as cautionary backdrop: Microsoft's OS-level "Sets" experiment (tabs in every app window, 2017–2019) was shelved for instability, later shipping only as simple File Explorer tabs ([Ars Technica](https://arstechnica.com/gadgets/2018/06/windows-sets-tabs-in-every-window-feature-wont-be-in-the-next-big-update), [ZDNet](https://www.zdnet.com/article/windows-10s-sets-feature-is-gone-and-not-expected-to-return)) — even platform vendors paid real costs for ambitious tab organization.

# 4. Is spatial-graph browsing actually better UX? (the honest answer)

### Direct answers

- **Is it genuinely different?** Yes. Spatial position is a real memory aid — the lab evidence is consistent (Data Mountain's statistically reliable retrieval advantage; GroupBar's faster task switching; Bergman's finding that people navigate to ~95% of *personal files* by spatial/folder navigation rather than search). Nobody confuses a canvas browser with a tab strip.
- **Is it genuinely better?** **Conditionally.** Better for a committed minority whose "corpus" is stable, personally built, and revisited often. Worse as a default for the mass market, because the three things that make tabs hard (they're numerous, transient, and constantly reflowed) are exactly the conditions under which spatial memory is weakest — and because the organization cost of manual curation loses to search's near-zero cost in every measured study.
- **Why has it never gone mainstream?** Measured adoption of *shipped* spatial features was ~0.01% (Panorama) and ~5.52% (Arc Spaces); curation actions are emotionally blocked by loss-anxiety ("as soon as something went out of sight, it was gone" — the "blackhole effect"); maintenance cost was high (24,000+ lines for Panorama; pixel-position storage that broke on resizes); and every vendor that survived converged on groups + search + AI suggestions instead.

### The evidence for (why it can work)

- **Spatial memory is real and exploitable.** Cockburn et al.'s standard monograph on spatial memory in interfaces ([Foundations and Trends in HCI](https://www.emerald.com/fthci/article/6/1/i/1324737/)); Uddin et al. (CHI 2021) showed visual landmarks help users build spatial memory of commands and become expert with them ([ACM](https://dl.acm.org/doi/fullHtml/10.1145/3411764.3445050)).
- **Tabs *are* used as external memory.** Dubroy & Balakrishnan's field study of 21 Firefox users found tabs function mainly as memory aids and buffers for forking exploration ([CHI 2010 PDF](https://dubroy.com/research/chi2010-a-study-of-tabbed-browsing.pdf) — single source). The spatial browser is a direct productization of that behavior.
- **It demonstrably works for stable, personally-built corpora.** Bergman's file-retrieval studies find users navigate to roughly **95% of their personal files via folder navigation**, not search — visual recognition cueing is a real mechanism ([recent paper](https://www.tandfonline.com/doi/full/10.1080/07370024.2024.2379838) — single source). One honest caveat on transferring that result: it was measured on **stable personal file collections**, not transient tabs. It supports spatial navigation only on the condition that your canvas becomes a stable, personally-built corpus — which is exactly why mechanic 1 (docked, hibernated, thumbnail-remembered nodes) matters more to this design than free-floating live tabs. Tiling window managers (i3, bspwm) are a thriving power-user niche — and the honest reading of them supports this report's rule rather than contradicting it: their users don't memorize user-chosen positions (the system arranges automatically, so positions shift); what they get is **zero curation cost** plus habitual keyboard workflows ([i3wm.org](https://i3wm.org)). That is evidence for "the system pays," not for stable user-placed spatial memory. Workona survives precisely by serving professionals whose work is recurring project tab-sets ([workona.com](https://workona.com) — single source). And infinite canvases (Miro/FigJam) are a mass-market success — for **bounded, collaborative, template-assisted** sessions where layout is the work product ([fig.com/figjam](https://www.figma.com/figjam)).

### The evidence against (why it lost every time it shipped)

- **The two hard adoption numbers both come from removals.** Panorama: ~0.01% of users ([Kruitbosch](https://www.gijsk.com/blog/2016/02/tab-groups-removal) — single source). Arc: 5.52% of daily users regularly used more than one Space — while 40% used Dia's AI tab chat ([Letter to Arc members](https://browsercompany.substack.com/p/letter-to-arc-members-2025) — single source). Arc's own retention profile resembled "a highly specialized professional tool (like a video editor)" — the stickiest users were "fanatics."
- **Manual curation has a recurring, conscious cost that loses to search.** Whittaker's study of 345 users performing 85,000 email-refinding events found preparatory foldering "does not improve retrieval success" ([IBM Research](https://research.ibm.com/publications/am-i-wasting-my-time-organizing-email-a-study-of-email-refinding), [ACM](https://dl.acm.org/doi/10.1145/1978942.1979457)). Revisitation research finds bookmarks — the *cheapest* curation act — are used for only ~2–3% of page revisitation ([Cockburn revisitation papers](https://citeseerx.ist.psu.edu/viewdoc/download?doi=10.1.1.117.8459&rep=rep1&type=pdf) — single source). A spatial canvas starts from an even lower base than a bookmark click.
- **Spatial memory is fuzzy and fragile at tab scale.** NN/g's synthesis: GUI spatial recall is "neighborhood-level" approximation, **breaks when layouts reflow** (their example: macOS Finder reflowing folder positions), degrades in deep structures, and matters most for repeat users ([NN/g on spatial memory](https://www.nngroup.com/articles/spatial-memory/) — single source). Panorama's own post-mortem names exactly this: absolute pixel positions that broke on window/screen changes.
- **Users are emotionally blocked from curation.** CHI 2021 ("When the Tab Comes Due"): ~25% of surveyed users had crashes from too many tabs; users keep tabs because "as soon as something went out of sight, it was gone" — a "blackhole effect" that resists closing, grouping, or archiving ([CMU news](https://www.cmu.edu/news/stories/archives/2021/may/overcoming-tab-overload.html), [ACM](https://dl.acm.org/doi/10.1145/3411764.3445585)). Any UI whose primary gesture is "organize your tabs" runs into this wall first.
- **Automatic grouping trades one failure for another.** Opera's auto-clustering "Tab Islands" (2023) shows the promise and fragility: users report islands silently dissolving after days — which destroys the stable positions spatial memory needs ([Opera forums](https://forums.opera.com/topic/66878/islands-for-tabs-disappear-after-few-days) — single source).
- **Even graph-style visualization inside knowledge tools is used as décor, not navigation.** Obsidian's graph view is persistently criticized as "looks great, but it's useless" for finding things; power users rely on search and curated lists ([community discussion](https://forum.obsidian.md/t/whats-the-point-of-the-graph-view-how-are-you-using-it/71316/11) — single source). A graph tab canvas must embed search, not replace it.

### The design levers that change the odds

Every lever attacks the curation cost instead of asking the user to pay it:

1. **Zero-effort capture and cleanup.** Third-party writeups of Arc describe auto-archive as default-on for unpinned tabs (12 hours, recoverable) with no visible off switch — the system taking the loss-anxiety action reversibly ([writeup](https://nestextended.com/arc-auto-archive-chrome) — single source; "un-disable-able" is that writeup's claim, not verified against Arc's own settings, which no longer ship updates). Whatever Arc's exact switch state was, the design point stands: make capture-and-cleanup the *default* and make it reversible. Your mechanic 1 (dock & hibernate with thumbnail) is this lever.
2. **The system proposes, the user confirms.** Chrome's AI Tab Organizer (Chrome 121, Jan 2024) scans tabs and suggests named groups ([Google blog](https://blog.google/products-and-platforms/products/chrome/google-chrome-generative-ai-features-january-2024)); CMU's Skeema research prototype — ML-suggested task groupings — measurably reduced tab stress ([CMU](https://www.cmu.edu/news/stories/archives/2021/may/overcoming-tab-overload.html)). Your mechanic 4 (suggest-only clustering) is this lever. **Never auto-move nodes** — Opera's dissolving islands and NN/g's stability rule both say reflow destroys the very memory the canvas exists to exploit.
3. **Search-first retrieval inside the canvas.** Tab search (Ctrl+Shift+A) is what actually scaled. Your palette (Blanc already has one) must be the primary retrieval tool; the graph is the memory aid around it.
4. **Memory-friendly canvas rules** (straight from NN/g): stable positions (never rearrange without consent), text labels + thumbnails (support imprecise visual search), breadth over depth, an overview/minimap, and "visit wear" landmarks.
5. **Session-scoped before persistent.** Miro/FigJam prove spatial layout works when it's a bounded collaborative *session*; Panorama failed as a permanent personal web. Ship the research-session canvas first; the decade-long personal graph is a later bet.

### The verdict, stated plainly

A spatial graph browser is a **genuinely different UX** whose benefits are real but **population-dependent**. If your product's default interaction is "manually arrange your tabs," history says you are building Panorama again. If its default is "browse normally; the browser builds the map for you, hibernates it for you, and suggests order — you confirm," you are building the one variant that has never been tried at product quality. That is the honest basis for going ahead.

## 5.2 The four mechanics, each with verdict / how / risk

**View states used throughout this section (and their real memory cost):** an **open** view is an attached, *visible* WebContentsView with a **running renderer** — real RAM and CPU, and the only thing that counts against the 6–8 interactive cap. A **retained** view is what Blanc's hibernate-with-`sessionStorage` path leaves behind: the view object stays attached but the *renderer process is discarded* **[audit]**, so it costs near-zero renderer memory — not literally zero (the view object and snapshot remain), but far below an open view. Retained views do **not** count against the interactive cap; Phase 1's exit check keeps an eye on them so the count can't creep. A **hibernated** node has no view at all: just a history snapshot plus your thumbnail. "Live view" in this report always means *open*.

### Mechanic 1 — Unified storage node (tab = card at a position, hibernatable)

| | |
|---|---|
| **Verdict** | **Buildable as designed.** ~80% exists in Blanc. |
| **How** | Extend the tab record built in `createTab` (`src/main/main.js:9457` **[verified this session]**) with `node: {x, y, w, h, parentId, edges}` and persist it through the existing versioned session pipeline (`captureWindowEntry` `main.js:6811` **[audit]**; `SESSION_WORKSPACE_VERSION = 2` at `src/main/session-workspace.js:11` **[verified this session]** — the module is deliberately Electron-free so migrations stay testable). "Saving" a node calls `quietTab` (`main.js:2721` **[audit]**) — Blanc's two-path discard kills the renderer but keeps a hidden view when `sessionStorage` exists, or keeps a history snapshot. Wake is `wakeTab` (`main.js:3124` **[audit]**), then place the re-attached view at node bounds via a `resizeNodes()` analog of `resizeActiveView` (`main.js:7277` **[audit]**). **Thumbnails are the one genuinely new piece:** Blanc's only `capturePage` use today is a 2px color probe, not full capture — so add `webContents.capturePage()` → PNG data-URL at hibernate time, copying the `navEpoch` staleness guard visible at `main.js:7852-7858` **[audit]** so a slow capture never annotates the wrong document. |
| **Risk** | Wake fidelity at scale: hundreds of hibernated nodes = hundreds of history replays, and thumbnail data-URLs bloat `session.json`. **Mitigate:** lazy wake (only on node click, never batch), store thumbnails in a separate `thumbs` store via the JsonStore primitive (one store, 250ms debounced, temp-file + sequence-checked rename — `src/main/store.js` **[audit]**), and respect `tab-sleep.js`'s snapshot-ceiling rule (it refuses rather than evicts). |

### Mechanic 2 — Automatic mind-mapping (clicking a link grows the graph)

| | |
|---|---|
| **Verdict** | **Buildable** — the interception skeleton already ships in Blanc. |
| **How** | The inert-tab guard at `src/main/tab-view.js:495-514` **[verified this session]** already does the core trick: `will-navigate` → `event.preventDefault()` → `setImmediate(() => createTab(targetUrl))` — a link click becomes a new tab instead of an in-place navigation (the code even documents *why* the `setImmediate` is there: "Not from inside this navigation event"). Generalize it: in graph mode, preventDefault the main-frame navigation, `createTab` as a **child** (`openerTabId` is already a `createTab` parameter **[verified in its signature]**; that it produces family-aware behavior downstream is per the audit, not re-verified), append an edge to the parent node, and position the child adjacent to the parent via a deterministic spiral/grid computed in a pure layout module modeled on `chrome-layout.js:58` **[verified this session]**. Route `target=_blank`/`window.open` through the per-tab `setWindowOpenHandler` (`tab-view.js:687-715` **[audit]**): `foreground-tab`/`background-tab` dispositions become child nodes; keep `new-window` popups and OS hand-offs exactly as Blanc has them so OAuth flows don't become graph soup. To distinguish real link clicks from JS redirects, tag clicks via the existing host-scoped preload bridge pattern (`tab-preload.js:60-330` **[audit]**). |
| **Risk** | SPA `pushState` navigations never fire `will-navigate` (missing edges) while programmatic redirects do (bogus edges). **Mitigate:** only fork navigations tagged by a recent link-click event; never fork POSTs or redirect chains; ship a global "linear mode" toggle as an escape hatch; measure edge quality on the 20 sites you actually use before trusting it. These rails are non-negotiable — a corrupted graph or a broken OAuth flow is a product-killing bug class. |

### Mechanic 3 — Drag-and-drop docking (arranging the canvas)

| | |
|---|---|
| **Verdict** | **Buildable with moderate new UI work** — the mechanic with the least existing Blanc code but the clearest reuse patterns. |
| **How** | Make the window's own webContents the **canvas document** — Blanc's strip already *is* the window document with page views layered above it (`main.js:13264` **[audit]**). The canvas doc paints the grid, edge lines, hibernated node cards (using your thumbnails), and a per-node chrome ring (title bar, close) in the margin around each live view's rect; live views sit above it, positioned by `setBounds` from one `resizeNodes()` analog of `resizeActiveView`. Dragging works because a WebContentsView only takes clicks inside its rect — the ring pixels around it belong to your canvas document. Track the pointer **main-side** with the `watchCursorFor` input-event pattern (`main.js:3779-3791` **[audit]**) rather than HTML5 drag-and-drop, which does not cross native view boundaries; send canvas → brain messages through trust-gated channels copying the `chromeOn`/`chromeHandle` pattern (`main.js:11369-11400` **[audit]**). **And build undo in from day one:** every canvas mutation — drag, delete, confirm-cluster move — must be an undoable command (Ctrl+Z with an entry list kept in the brain, not the canvas document), and node deletion routes through Blanc's closed-tab undo machinery rather than destroying anything (`closed-tabs.js` 3-tier system **[audit]**). This is not polish: section 4's core evidence is loss-anxiety, and an irreversible-feeling canvas recreates it. |
| **Risk** | **Pan/zoom is the one place Electron gives no headroom:** moving every live view every frame stutters with many views. **Mitigate:** cap simultaneous live views at 6–8 (mechanic 1 makes hibernation cheap, so the cap is painless), coalesce bounds updates to one change-only send per frame (the island proximity throttle pattern, `main.js:3646-3713` **[audit]**), and implement zoom as a canvas-document CSS transform with view re-layout **on settle**, not per frame. Also respect the gotchas: a transparent pixel still takes clicks (`island-autohide.js:157-162` **[audit]**), and don't let a fully covered chrome document go occluded on Windows/Linux — leave the 1px row trick in place. **When the cap is exceeded, never refuse:** opening the 9th node *quiets the least-recently-focused open node automatically* (through the existing `quietTab` machinery — cheap and reversible, see mechanic 1) with an undo toast. |

## 5.3 Architecture sketch: the spatial browser on Blanc

```
┌───────────────────────────────────────────────────────────────────┐
│  BrowserWindow (frameless, one per workspace)                     │
│                                                                   │
│   ┌─────────────────────────────────────────────────────────┐    │
│   │ TOP   Transparent overlay WebContentsView               │    │
│   │       (island panel/palette/permissions — unchanged)    │    │
│   ├─────────────────────────────────────────────────────────┤    │
│   │ MID    Live page WebContentsViews — ONE PER OPEN NODE   │    │
│   │        placed by setBounds at that node's rect;         │    │
│   │        capped at 6–8 live; everything else hibernated   │    │
│   ├─────────────────────────────────────────────────────────┤    │
│   │ BASE   The window's own document = THE CANVAS           │    │
│   │        grid · edge lines · hibernated node cards        │    │
│   │        (thumbnail + title) · per-node chrome rings      │    │
│   │        minimap · search palette results                 │    │
│   └─────────────────────────────────────────────────────────┘    │
└───────────────────────────────────────────────────────────────────┘
  MAIN PROCESS (the brain) — new modules in Blanc's pure style:
    node-model.js        (pure: nodes, edges, parents, ordering)
    canvas-layout.js     (pure: rects, spiral placement, pan/zoom math)
    graph-ipc.js         (trust-gated channels, chromeOn pattern)
    graph-embedder.js    (worker_thread + MiniLM ONNX)
  PERSISTENCE (all via the one JsonStore primitive, store.js):
    session.json  v2 + node records {x,y,w,h,parentId,edges}
    thumbs.json   (PNG data-URLs, lazy-written)
    vectors.json  (384-dim embeddings)
    REUSED FROM BLANC UNCHANGED:
      quietTab / wakeTab (hibernate & wake) · tab-sleep eligibility
      chromeOn/chromeHandle trust gates · chrome-layout.js sizing
      adblock · sessions · closed-tab undo
      (the bundled updater is a decision, not a given — see Phase 3)
```

The data flow mirrors Blanc's existing one-way pipeline: Chromium events mutate the brain's node records → one broadcast (`tabs:updated`-style payload) persists the session *and* repaints every chrome surface — so "no tab change can be drawn but not saved" (an IPC-audit finding: one broadcast does persistence, sync fingerprinting, and the payload push in a single call).

## 5.4 Coexistence: how the island and the canvas share the screen

§5.3 leaves one question implicit that your first AI session will hit immediately: *what survives of Blanc's UI?* Here is the initial spec — these are **design decisions to implement, not verified code** (nothing here exists in Blanc yet):

- **The island survives unchanged.** It stays the command surface — palette, find, shield, settings. What the canvas replaces is the *tab strip's* job, not the island's. No island code needs to change for Phases 0–1.
- **One source of truth.** The island's tab list and the canvas cards are two views of the *same* node records in the brain; Blanc's existing one-broadcast pattern (above) updates both. Never let the canvas document keep its own copy of state — that's how the two views drift apart.
- **Ctrl+T / the island's "+" on a canvas** creates a new node at an auto-placed position — a deterministic spiral step from the last-focused node, computed in the pure `canvas-layout.js` module — and then focuses it. The user can drag it wherever they want afterwards.
- **Opening a node from the island's list** pans the canvas to that node (animated), waking it first if it was hibernated.
- **What each state looks like:** hibernated nodes are cards (thumbnail + title); open nodes are live windows with a per-node chrome ring; the ring is draggable, the page inside is not (the page owns its own pixels).
- **Linear mode** is a settings toggle that renders the canvas as Blanc's normal full-pane layout — the escape hatch from mechanic 2 and the fallback when the canvas misbehaves on a site you need.
- **The 9th-node rule lives here too:** exceeding the 6–8 open cap *quiets the least-recently-focused open node automatically* (via the existing `quietTab` machinery, cheap and reversible) with an undo toast — never a refusal, never a modal dialog.

## Phase 1 — The canvas + one live view + hibernation (≈ weeks 3–6)

4. **Build the canvas document** as a new `blanc-chrome://` host served through Blanc's existing fail-closed protocol pattern (`chrome-protocol.js` per-host allowlist **[audit]**) — generalize how the strip document is loaded into the window (`main.js:13264` **[audit]**). ## Phase 2 — Docking, clustering, polish (≈ weeks 7–12)

8. **Drag-and-drop docking — with undo.** Canvas-ring drags via main-side pointer tracking (`watchCursorFor` pattern, `main.js:3779-3791` **[audit]**); strip/island drags via one trust-gated IPC channel copying `chromeOn` **[audit]**. Every mutation (drag, delete, confirm-cluster move) goes through an undoable command list (Ctrl+Z) kept in the brain; node deletion routes through Blanc's closed-tab undo machinery rather than destroying anything (`closed-tabs.js` **[audit]**). **Exit check:** drag a live node by its ring; drop a hibernated card onto a new position; both persist across restart; Ctrl+Z reverses a drag, a delete, *and* a cluster-confirmed move; nothing overlaps the 1px occlusion row.
9. **Semantic clustering, suggest-only.** Bundle the MiniLM ONNX file; `worker_thread` embedder; feed the matrix into the existing `proposeFromEmbeddings` (`tab-import-organizer.js:370` **[verified this session]**); highlight proposed clusters with generated names; animate toward centroids only on confirm. **Exit check:** 15 docked nodes from a research session produce ≥1 sensible named cluster proposal; nothing ever moves without a click; embedding one new node takes **under 500 ms on your machine** (measure it — the "tens of ms" figure is a modern-CPU best case).
10. **Search-first retrieval.** Wire the existing island palette to canvas nodes (jump-to-node, "find node by title/URL"). **Exit check (measurable):** on a 40-node canvas, time yourself finding 5 preset targets two ways — by eye, then via search. Search must take **under half** the manual time, **twice in a row**. This is your hedge against risk #1, and it's non-negotiable.
11. **A safety net for the canvas.** The canvas *is* the user's research memory; losing it is the worst failure this product can have. Add three things: a user-facing **Export canvas** (one JSON file + a thumbnails folder); **automatic rolling backups** of `session.json`/`thumbs.json` (JsonStore writes are already atomic — temp-file + sequence-checked rename, `src/main/store.js` **[audit]** — but atomic ≠ recoverable: a corrupt file falls back to empty defaults, so keep timestamped copies); and a restore flow. **Exit check:** delete `session.json` by hand, restore from backup, and confirm the full canvas — nodes, edges, thumbnails — comes back intact.
12. **Harden and test.** Put node/edge policy and canvas layout in pure modules and port Blanc's `node --test` culture (see `session-workspace.js:4-5` **[verified this session]**: "Keep this module Electron-free: migrations and rollback precedence must be fixture-testable"). Exercise the trust model: your new channels must reject unregistered senders exactly like `chromeOn` does. **Exit check:** the pure tests pass on plain `node --test`; a hand-crafted IPC message from a non-surface webContents is refused.

**Throughout:** keep a private build log; when AI-generated code touches `main.js`, prefer *new functions/modules + one-line hooks* over edits inside existing functions; and re-read the "copy this / avoid this" boxes in section 1 before each phase — they are distilled from bugs Blanc already paid to fix.

## Phase 3 — Business realities (before you ship to anyone else)

Not code tasks — but skipping them is how founders get burned, and risk #1 says economics is the fatal one:

- **Code signing.** An unsigned Windows installer triggers SmartScreen's "unknown publisher" warning — and for a *browser*, users are trained to distrust exactly that. A code-signing certificate costs real money (order of a few hundred US$ per year; prices change, so check current OV-vs-EV options before launch — guidance, not a verified figure).
- **Update distribution — settle the server-dependency decision explicitly.** Blanc bundles `electron-updater`, but an updater needs a hosted, signed feed (e.g., GitHub Releases). Pick one: (a) host a feed — a real server dependency, though GitHub-hosted keeps it cheap and versioned; or (b) disable auto-update and distribute signed installers manually. Don't leave it defaulted-on pointing at Blanc's own feed — that ships your users' update checks to someone else's server.
- **Pricing.** Section 3 is the reference: the surviving niche charges $5–13/mo, and the best hard revenue number in the category is ~$1.5M ARR (one company). A free tool for your own use is a fine goal through Phase 2; a paid product needs the gate below.
- **Decision gate.** Spend nothing on signing, hosting, or marketing until roughly **10 strangers use the browser weekly** and at least one volunteers to pay. Every prior attempt in section 2 died of adoption economics — this gate is the cheapest possible test of whether yours won't.
